# 성좌 × 헌터 페어커 전투 시스템 구현 요구사항

> 이 문서는 Claude Code에 그대로 전달하기 위한 구현 요구사항서다.
> 문서 맨 끝의 **41. 구현 지시**가 최종 작업 지시문이다.

---

# 1. 프로젝트 목적

성좌 × 헌터 1:1 페어를 기반으로 진행되는 자캐 커뮤니티의 **웹 기반 전투 시스템**을 제작한다.

이 시스템의 목적은 전투 연출용 홈페이지가 아니라, 실제 커뮤니티 진행 중 참가자와 운영진이 사용할 수 있는 **전투 진행 도구**를 만드는 것이다.

핵심 구조는 다음과 같다.

* 헌터와 성좌는 1:1 페어
* 페어 1조 vs 몬스터 전투와, 다수 페어가 참여하는 레이드를 모두 지원
* 페어 한쪽이 이탈해도 남은 참가자가 진행할 수 있는 자동 행동 제공
* 헌터와 성좌는 각각 행동 가능
* 헌터와 성좌는 각각 별도의 행동력을 보유
* 포인트는 행동력과 별개인 상점 화폐
* 헌터와 성좌의 행동 조합에 따라 페어 연계 발생
* 적에게 HP, 상태이상, 패턴 등이 존재
* 전투는 라운드제로 진행
* 운영진이 최종 전투 결과를 관리
* 전투 결과를 로그 형태로 확인 가능

초기 버전에서는 **전투 기능을 우선 구현**하고, 세계관 소개 페이지 등의 기능은 만들지 않는다.

기존 소개 홈페이지(`/`)는 제거하거나 대체하지 않고 그대로 유지하며, 전투 시스템은 **별도 페이지로 추가**한다.

# 2. 기술 요구사항

현재 사용 중인 Astro 프로젝트에 추가할 수 있는 구조로 제작한다.

권장 구성:

* Astro
* TypeScript
* 필요한 경우 React (전투 화면처럼 상태가 많은 화면에만 사용)
* CSS
* GitHub Pages 배포 가능

GitHub Pages에서 작동해야 하므로 서버가 반드시 필요한 구조로 만들지 않는다.

초기 버전에서는 LocalStorage를 이용해 데이터를 저장해도 된다.

추후 Supabase 등의 DB를 붙일 수 있도록 데이터 처리 부분은 UI와 최대한 분리한다.

## 2.1 권장 디렉터리 구조

아래 구조는 권장안이며, 더 나은 구성이 있으면 조정해도 된다.
단 **설정값 / 규칙 엔진 / 저장 계층 / UI**가 서로 분리되어야 한다는 원칙은 유지한다.

```text
src/
├── pages/
│   ├── index.astro              기존 소개 페이지 (유지, 수정 금지)
│   └── battle/
│       ├── index.astro          참가자 전투 단말
│       └── control.astro        운영진 작전실
│
├── battle/
│   ├── config/                  ← 모든 수치는 여기서만 정의
│   │   ├── rules.ts             행동력, 회복량, 부상/계약 단계 기준
│   │   ├── actions.ts           기본 행동 목록과 비용
│   │   ├── combos.ts            페어 연계 조건과 결과
│   │   ├── status.ts            상태이상 정의
│   │   └── rewards.ts           포인트 보상표
│   │
│   ├── types/                   데이터 모델 (TypeScript 타입)
│   │
│   ├── engine/                  전투 규칙 — 순수 함수, UI 의존 없음
│   │   ├── round.ts             라운드 진행
│   │   ├── damage.ts            피해 계산
│   │   ├── combo.ts             연계 판정
│   │   └── status.ts            상태이상 처리
│   │
│   ├── store/                   저장 계층
│   │   ├── StorageAdapter.ts    인터페이스 정의
│   │   ├── LocalStorageAdapter.ts
│   │   └── index.ts             어댑터 선택 지점
│   │
│   └── ui/                      화면 컴포넌트
│
└── styles/
    ├── global.css               기존 소개 페이지 스타일 (유지)
    └── console.css              전투 콘솔 테마
```

## 2.2 저장 계층 인터페이스

LocalStorage는 **구현체 하나**일 뿐이며, 나중에 Supabase 어댑터로 교체 가능해야 한다.
UI와 엔진은 `StorageAdapter` 인터페이스만 알고 있어야 하고, LocalStorage API를 직접 호출해서는 안 된다.

```ts
interface StorageAdapter {
  loadBattle(id: string): Promise<BattleState | null>;
  saveBattle(state: BattleState): Promise<void>;
  listBattles(): Promise<BattleSummary[]>;
  deleteBattle(id: string): Promise<void>;
  exportAll(): Promise<string>;      // JSON 문자열
  importAll(json: string): Promise<void>;
}
```

모든 메서드는 동기 구현이어도 `Promise`를 반환한다. 나중에 네트워크 기반으로 바뀌어도 호출부를 수정할 필요가 없어야 한다.

# 3. 전투 기본 구조

전투는 **라운드제**다.

한 페어는 다음 두 캐릭터로 구성된다.

```text
PAIR
├── HUNTER
└── CONSTELLATION
```

헌터와 성좌는 각각 자신의 행동력을 가지고 있다.

기본값:

```text
헌터 최대 행동력: 5
성좌 최대 행동력: 5

전투 시작:
각자 행동력 최대치

라운드 시작:
각자 행동력 +2

최대 행동력을 초과하여 회복 불가
```

전투 중 부상이나 상태이상 등에 의해 최대 행동력이 변경될 수 있는 구조로 작성한다.

수치는 추후 쉽게 수정할 수 있도록 하드코딩을 최소화한다.

## 3.1 전투 규모 — 단일 전투와 레이드

전투는 두 규모를 모두 지원한다.

```text
DUEL   페어 1조 vs 몬스터
RAID   다수 페어가 같은 적을 공동 공략
```

**데이터 구조는 하나로 통일한다.** 전투는 항상 `페어 배열 + 적 배열`을 가지며,
DUEL 은 페어가 하나뿐인 레이드로 취급한다. 규모별로 별도 로직을 두지 않는다.

레이드에서 추가로 필요한 것:

* 페어별로 각각 행동을 제출한다
* 적이 여러 체일 수 있고, 페어는 공격 대상을 선택한다
* 여러 페어의 피해를 적 단위로 합산한다
* 적의 공격 대상은 규칙에 따라 결정한다 (기본: 라운드마다 순환)
* 참가자 화면에서 다른 페어의 상태와 제출 여부를 확인할 수 있다
* 모든 페어가 제출되었을 때 라운드를 처리한다

광역 공격과 다수 대상 패턴은 Phase 4 에서 추가한다.

## 3.2 자동 행동

페어 한쪽이 중간에 이탈하거나 응답하지 않아도 **남은 참가자는 계속 진행할 수 있어야 한다.**

조작 주체는 다음 두 상태를 가진다.

```text
ACTIVE   참가자가 직접 조작
AUTO     자동 행동에 위임
```

자동 행동이 적용되는 경우:

* 조작 주체가 AUTO 인 경우
* 라운드 처리 시점까지 행동이 제출되지 않은 경우
* 선택한 행동이 처리 시점에 사용 불가가 된 경우 (행동력 부족, 대상 소멸 등)

자동 행동 규칙은 **데이터로 정의하고 위에서부터 검사해 첫 번째로 조건을 만족하는 행동을 쓴다.**
조건에는 HP 비율, 남은 행동력, 대상 상태 등을 사용할 수 있다.

기본 정책:

```text
HUNTER
  HP 40% 미만이고 행동력 1 이상   → 방어
  행동력 1 이상                   → 기본 공격
  그 외                           → 대기

CONSTELLATION
  적 방어력이 있고 행동력 1 이상  → 방어력 감소
  행동력 1 이상                   → 버프
  그 외                           → 관측
```

**자동 행동이 지켜야 할 것:**

* 현신, 아이템처럼 소모가 크거나 되돌릴 수 없는 행동은 절대 자동으로 사용하지 않는다
* 생존을 우선한다
* 자동으로 처리된 항목은 로그와 화면에 `AUTO` 로 명확히 표시한다
* 참가자가 돌아오면 즉시 직접 조작으로 되돌릴 수 있다

행동을 아예 하지 않는 선택지(헌터 `대기` / 성좌 `관측`, 행동력 0)를 기본 행동으로 함께 제공한다.

## 3.3 캐릭터 시트와 스탯

전투 수치는 직접 입력하지 않는다. **캐릭터 시트에서 파생한다.**

```text
캐릭터 시트 (스탯 + 클래스)
        ↓  파생
전투 상태 (HP / 공격력 / 방어력 / 행동력 / 권능 배율)
```

전투 중 운영진이 수치를 바꿔도 **시트 원본은 변하지 않는다.**
프리셋 NPC 도 같은 파생 경로를 통과한다 — NPC 만 다른 계산식을 쓰는 일이 생기면 안 된다.

### 스탯 배분

```text
모든 스탯 시작값     1
자유 배분 포인트     12
스탯 하나의 상한     6
```

**헌터 스탯**

| 스탯 | 이름 | 효과 |
| --- | --- | --- |
| STR | 근력 | 공격력 +1.2 / 1점 |
| VIT | 체력 | 최대 HP +8 / 1점 |
| AGI | 민첩 | 방어력 +0.8 / 1점 · 회피 판정 |
| SEN | 감각 | 기믹 판정 · 약점 포착 (PHASE 3) |
| WIL | 의지 | 상태이상 저항 (PHASE 2) |

**성좌 스탯**

| 스탯 | 이름 | 효과 |
| --- | --- | --- |
| AUT | 권능 | 버프 · 디버프 효과 +4% / 1점 |
| DIV | 신격 | 최대 행동력 +1 / 3점 |
| RES | 공명 | 계약 안정도 회복 (PHASE 3) |
| OBS | 관측 | 계시 정확도 (PHASE 2) |
| MAN | 현신 | 현신 위력 · 반동 경감 (PHASE 3) |

아직 반영되지 않는 스탯도 시트에는 존재하며, **어느 단계에서 동작하는지 화면에 표시한다.**
스탯을 추가·수정할 때 UI 와 엔진 코드를 고치지 않아도 되도록 정의를 데이터로 둔다.

### 파생 공식

```text
헌터
  최대 HP  = 기본 60 + VIT × 8   + 클래스 보정
  공격력   = 기본 4  + STR × 1.2 + 클래스 보정
  방어력   =          AGI × 0.8  + 클래스 보정
  최대 AP  = 기본 5             + 클래스 보정

성좌
  권능 배율 = 1 + AUT × 0.04     + 권역 보정
  최대 AP   = 기본 5 + floor(DIV / 3) + 권역 보정
```

헌터의 방어력은 받는 피해를 **상수로** 깎고, 방어 행동은 **비율로** 깎는다.
성좌의 권능 배율은 버프·디버프 수치에 곱해지며, 성좌 상태 패널티가 다시 곱해진다.

### 클래스 · 권역

헌터는 **클래스**, 성좌는 **권역**을 하나 고른다.

```text
HUNTER
  STRIKER    근접 격퇴형    공격력 +3, 최대 HP +5
  GUARDIAN   방어 전담형    최대 HP +25, 방어력 +3, 공격력 -1
  RANGER     원거리 사격형  공격력 +2, 최대 HP -5, 방어력 -1
  CASTER     권능 술사형    공격력 +1, 최대 행동력 +1
  MEDIC      구조 지원형    최대 HP +12, 방어력 +1

CONSTELLATION
  WAR        전투 권역      권능 배율 +10%
  GUARD      수호 권역      권능 배율 +5%, 최대 행동력 +1
  OMEN       예지 권역      최대 행동력 +1
  CALAMITY   재앙 권역      권능 배율 +15%
  GRACE      은총 권역      최대 행동력 +1
```

클래스별 고유 특성(보호 보정, 구조 보정, 계시 확장 등)은 `config/characters.ts` 의
`traits` 로 정의하고, 라운드 처리 중에 `engine/traits.ts` 가 해석한다.

```text
GUARDIAN   보호 효과 +40% · 피해 감소 부여 +20%
RANGER     약점이 드러난 적에게 피해 +25%
CASTER     성좌에게 받는 공격력 버프 +25%
MEDIC      구조 회복 +50% · 회복량 +30%
GUARD      피해 감소 부여 +50% · 보호 효과 +20%
OMEN       계시가 공략조 전체에 공유됨
CALAMITY   부여하는 상태이상 지속 +1 라운드
GRACE      회복량 +40% · 구조 회복 +30%
```

아직 붙이지 않은 특성이 생기면 `pending` 에 적어 **무엇이 미구현인지 시트에 표시한다.**
지금은 비어 있다.

## 3.4 계정과 진입 흐름

회원가입이 곧 **캐릭터 시트 작성**이다.

```text
계약자 등록 (/battle/join/)
  역할 선택 → 계정 → 시트 작성 → 스탯 배분
        ↓
전투 단말 (/battle/)
  페어 상대 선택 → 전투 규모 선택 → 출격
```

* 전투 단말은 등록을 마친 참가자만 진입할 수 있다
* 전투 상태는 로그인한 계정의 시트에서 파생된다
* 페어 상대가 아직 등록되지 않았으면 프리셋 캐릭터와 계약해 진행할 수 있다
* 전투는 계정 단위로 저장되어 새로고침 후에도 이어진다

### 서버 없는 단계의 제약 — 반드시 알려야 한다

GitHub Pages 에는 서버가 없다. 따라서 이 단계의 계정은 **인증이 아니다.**

```text
· 계정과 비밀번호 해시가 같은 브라우저에 저장된다 → 위조를 막을 수 없다
· 다른 기기·다른 사람의 시트는 조회되지 않는다
· 브라우저 데이터를 지우면 시트도 사라진다
```

그래서 다음을 지킨다.

1. 계정 기능은 `AuthAdapter` 인터페이스 뒤에 두고, UI 는 구현체를 알지 않는다
2. 화면에 위 제약을 명시한다 — 참가자가 진짜 계정으로 오해하면 안 된다
3. 비밀번호는 평문으로 저장하지 않는다 (SHA-256 해시)
4. 다른 참가자 목록은 공개 가능한 정보만 노출한다 (이름 · 역할 · 클래스)

서버 또는 Supabase Auth 를 붙이면 `AuthAdapter` 구현체만 교체한다.
캐릭터 시트 · 스탯 · 파생 공식은 그대로 재사용된다.

# 4. 전투 진행 순서

기본적인 한 라운드는 다음 순서로 진행한다.

```text
ROUND START
↓
적 상태 및 패턴 공개
↓
헌터 행동 선택
↓
성좌 행동 선택
↓
행동 확정
↓
버프 / 디버프 처리
↓
헌터 / 성좌 행동 처리
↓
페어 연계 확인
↓
적 행동 처리
↓
피해 및 상태이상 정산
↓
ROUND END
↓
다음 ROUND
```

운영진이 필요하면 자동 처리 결과를 수정할 수 있어야 한다.

# 5. 헌터

헌터는 전장에 직접 참여하는 캐릭터다.

기본적으로 다음 행동을 사용할 수 있다.

| 행동 | 기본 행동력 | 설명 |
| --- | --- | --- |
| 기본 공격 | 1 | 적에게 피해를 준다. |
| 기본 방어 | 1 | 해당 라운드에 받는 피해를 감소시킨다. |
| 일반 스킬 | 2 | 캐릭터마다 서로 다른 커스텀 스킬을 등록할 수 있어야 한다. |
| 강력한 스킬 | 3 | 일반 스킬보다 강력한 효과를 가진다. |
| 보호 | 2 | 다른 캐릭터를 보호한다. |
| 구조 | 2 | 전투 불능 상태의 다른 캐릭터를 구조한다. |
| 기믹 수행 | 1~2 | 보스전 등에서 특정 기믹을 수행한다. |
| 아이템 | 0~1 | 소지한 아이템을 사용한다. 비용은 아이템별로 다르다. |

# 6. 성좌

성좌는 계약한 헌터에게 권능을 제공하는 역할이다.

## 6.1 버프 — 행동력 1

예:

* 공격력 증가
* 방어력 증가
* 명중 증가
* 회피 증가
* 상태이상 저항
* 피해 감소

강력한 버프는 행동력 2를 사용할 수 있다.

같은 종류의 버프가 중첩될 경우 처리 방식을 설정할 수 있도록 구조화한다.

초기 기본값은:

```text
동일 버프 중첩 불가
더 높은 효과 우선
```

## 6.2 디버프 — 행동력 1

예:

* 적 공격력 감소
* 적 방어력 감소
* 행동 제한
* 받는 피해 증가
* 회복 차단
* 약점 노출
* 스킬 봉쇄

강력한 디버프는 행동력 2.

## 6.3 계시 — 행동력 2

적의 패턴 또는 기믹 정보를 확인한다.

## 6.4 부분 현신 — 행동력 3

성좌가 일부 권능을 직접 전장에 구현한다.

전투당 사용 횟수를 제한할 수 있도록 한다.

## 6.5 완전 현신 — 행동력 5

성좌가 직접 전장에 개입한다.

공략 전체 또는 특정 기간 동안 사용 횟수를 제한할 수 있도록 한다.

## 6.6 아이템

성좌 전용 성유물 또는 공용 아이템을 사용한다.

# 8. 페어 연계 시스템

헌터와 성좌가 같은 라운드에 특정 행동 조합을 사용하면 **페어 연계**가 발생할 수 있다.

초기 연계는 다음과 같다.

### 공격 연계

```text
성좌: 방어력 감소 / 약점 노출
  +
헌터: 공격 스킬
```

결과 예: 추가 피해 / 방어 일부 무시 / 약점 공격

### 방어 연계

```text
헌터: 방어
  +
성좌: 보호 버프
```

결과: 추가 피해 감소 / 반격 가능

### 제압 연계

```text
성좌: 행동 제한 디버프
  +
헌터: 상태이상 공격
```

결과: 상태이상 성공률 증가 / 적 행동 취소 가능

### 구조 연계

```text
성좌: 이동 / 보호 버프
  +
헌터: 구조
```

결과: 구조 행동 보정 / 구조 대상 추가 피해 방지

### 현신 연계

```text
헌터: 구속 / 약점 노출
  +
성좌: 현신
```

결과: 현신 공격 강화 / 현신 반동 감소

**연계 자체에는 추가 행동력을 소비하지 않는다.**

연계 조건은 추후 운영진이 추가/수정할 수 있도록 `config/combos.ts`에 데이터로 정의한다.
새 연계를 추가할 때 엔진 코드를 수정해야 한다면 잘못된 설계다.

# 16. 포인트

포인트는 행동력과 완전히 별개의 자원이며 **개인 상점 화폐**로 사용한다.

전투 화면에서는 현재 보유 포인트만 확인할 수 있도록 한다.

**전투 중 포인트로 행동력을 구매하거나 스킬을 사용하는 기능은 만들지 않는다.**

포인트와 보급품은 **개인 소유**다 (`CharacterSheet.points` · `inventory`).
페어와 나누지 않는다 — 각자 벌고, 각자 산다.

**전투 안에서도 합치지 않는다.** 각자 자기 가방을 들고 들어가고, 쓴 것은 쓴 사람의
가방에서만 빠진다. 상대의 가방에서 꺼내 쓸 수 없다 — 넘기려면 선물해야 한다.

```text
포인트   얻은 만큼을 두 사람 모두에게 준다 (나누지 않는다)
         운영진은 한 사람만 지목해 줄 수도 있다
가방     사람마다 따로. 빈손이면 기본 보급을 받되, 그 주체가 쓸 수 있는 것만 받는다
정산     전투가 끝난 시점의 개인 소지금 · 가방을 시트에 그대로 옮겨 적는다
         나눌 것이 없으므로 두 번 정산해도 값이 달라지지 않는다
```

어디에서 보이는가:

```text
보급 상점  /battle/shop/  — 진열 전체와 내 소지금 · 가방. 여기서 직접 사고 반납한다
내 시트    SUPPLY 절 — 소지금 · 가방 · 가격표 (상점으로 넘어가는 입구)
프로필     06 보급 · 포인트
작전실     보급 창구 — 사람마다 열린다. 운영진이 소지금 · 보급품을 직접 줄 수도 있다
전투 화면  보유량 확인과 사용 (구매는 불가)
```

**전투에 배치된 동안에는 살 수 없다.** 보급은 전투 밖에서만 갖춘다.

```text
배치 판정   진행 중인 전투(CLEARED · FAILED 가 아닌)의 페어에 내 계정이 있으면 창구를 닫는다
누를 때     화면을 열어 둔 사이 배치될 수 있으므로 버튼을 누른 순간 한 번 더 확인한다
```

포인트 지급 · 차감과 대리 구매는 관리국이 한다. 반납은 구매가의 절반을 돌려준다.

**값은 서버가 정한다.** 브라우저가 계산해 시트를 저장하면, 본인 시트를 고칠 수 있는
참가자가 소지금을 스스로 올릴 수 있다. 그래서 세 겹으로 막는다.

```text
1) 진열      가격 · 한도는 shop_items 에 있다 (코드의 기본 목록도 서버에 심어 둔다)
2) 트리거    참가자가 sheets.points · inventory · stat_bonus 를 직접 고치면 거절한다
             운영진은 통과한다 — 지급 · 차감이 그들의 일이다
3) 창구 함수 shop_trade(구매 · 반납) · shop_gift(선물) · use_supply(강화)로만 바꾼다
             소지금 · 한도 · 배치 여부를 서버가 다시 보고, 지갑을 서버가 고쳐 돌려준다
```

화면의 버튼 잠금은 미리 알려 주기 위한 것이다 — 통과 여부는 언제나 서버가 정한다.

## 16.1 선물하기

**이름**(헌터의 이름 · 성좌의 성호)으로 상대를 찾아 소지금이나 보급품을 넘긴다
(`shop_gift`). 받는 쪽의 보유 한도를 넘겨 보낼 수 없고, 어느 한쪽이라도 전투에
배치돼 있으면 닫힌다.

이름으로 찾으려면 이름이 겹치지 않아야 한다 — **이름은 참가자마다 하나뿐이다.**

```text
유니크    lower(btrim(name)) 에 유니크 색인 (0018)
          대소문자와 앞뒤 공백은 같은 이름으로 본다
찾기      색인과 **같은 식**으로 찾는다 — 두 사람이 걸릴 자리를 만들지 않는다
겹치면    0018 은 아무것도 바꾸지 않고 멈추고, 누가 겹치는지 알려 준다
          작전실에서 한쪽 이름을 고친 뒤 다시 실행한다
```

## 16.2 능력치 강화

전투 밖에서 쓰는 보급품이 시트의 `statBonus` 를 영구히 올린다 (`use_supply`).
배분 점수(12점 · 상한 6)와 따로 세는 값이라 시트 검증은 이 값을 보지 않는다.
한 능력치에 쌓을 수 있는 상한(`effect.statCap`)은 **운영진이 진열에서 정한다**.

서버가 판정하므로 강화 품목의 정의는 `shop_items.item` 에도 함께 있어야 한다
(마이그레이션 0017 이 기본 품목을 심는다).

## 16.3 상점 진열 — 운영진이 직접 넣는다

기본 품목은 코드(`config/items.ts` · `config/shop.ts`)에 남는다.
작전실 **상점 탭**은 그 위에 얹는 층이다 (`shop_items`).

```text
기본 품목의 가격 · 한도를 고친다
진열에서 뺀다 (active = false)
없던 품목을 새로 만든다 — 이름 · 분류 · 대상 · AP · 전투 중 사용 · 효과까지
```

새로 만든 품목도 전투에서 그대로 쓰인다. 엔진은 아이템을 이름으로 알지 않고
`effect` 필드만 해석하므로, 창구에서 넣은 값이 곧 판정에 들어간다.

기본 보상 데이터:

```text
일반 층 클리어    100P
보스 층 클리어    300P
서브 임무         50~150P
다른 페어 구조    100P
숨겨진 기믹       80P
진영 임무         100~200P
```

수치는 설정 파일(`config/rewards.ts`)에서 수정 가능해야 한다.

자동 지급(층 클리어 · 다른 페어 구조 · 숨겨진 기믹)은 라운드 처리에서 원장에 기록되고,
서브 임무와 진영 임무는 운영진이 직접 지급한다.
합계만 남기면 근거를 잃으므로 **지급 내역을 반드시 원장에 남긴다.**

# 17. UI 디자인 — 헌터 관리국 작전 시스템

전투 시스템 UI는 **정부 헌터 관리국이 실제로 사용하는 전투 통제 시스템**처럼 디자인한다.

세계관 소개 홈페이지와는 달리, 전투 페이지는 감성적인 판타지 화면보다 **정보 전달과 조작성을 우선하는 작전용 인터페이스**로 제작한다.

전체적인 인상:

* 헌터 관리국 전산 시스템
* 국가 재난 대응 센터
* 탑 공략 작전 콘솔
* 실시간 전투 상황판
* 군·재난 통제실 UI
* 성좌 계약 모니터링 시스템

다만 지나치게 현대 군사 UI만 사용하지 말고, **성좌와 탑을 나타내는 별자리·성흔·권능 요소**를 함께 섞는다.

예:

```text
HUNTER MANAGEMENT AGENCY
TOWER RAID CONTROL SYSTEM

OPERATION : FIRST TOWER
FLOOR : 37
ROUND : 04
STATUS : ENGAGED
```

## 17.1 기존 디자인 시스템과의 관계

기존 소개 페이지(`global.css`)에서 **재사용할 것**:

* 다크 배경 톤과 별빛 질감
* 성좌 = 금색/보라, 헌터 = 청색 계열의 색 의미
* 폰트 스택 (Pretendard 본문 / Cinzel 영문 라벨)

전투 페이지에서 **새로 만들 것**:

* 콘솔 전용 스타일시트 (`console.css`)
* 모노스페이스 수치 표기, 라벨형 타이포그래피
* 각진 패널, 얇은 구분선, 게이지 바
* 소개 페이지의 둥근 카드 · 큰 세리프 제목 · 여백 위주 레이아웃은 **사용하지 않는다**

즉 같은 세계관의 팔레트를 공유하되, 레이아웃 언어는 별개다.

# 18. 기본 색상과 스타일

방향:

* 배경: 검정 / 짙은 남색 / 짙은 회색
* 기본 UI: 청회색 또는 어두운 회색
* 정상 상태: 청록색
* 경고: 노란색
* 위험: 주황색
* 치명적 상태: 빨간색
* 성좌 관련 정보: 금색 / 보라색 / 별빛 계열
* 헌터 관련 정보: 청색 / 백색

색상은 단순 장식이 아니라 **상태 표현**에 사용한다.

```text
NORMAL           청록
WARNING          노랑
CRITICAL         빨강
OFFLINE          회색
CONSTELLATION    금색
```

텍스트는 모니터링 시스템처럼 간결하고 수치 중심으로 보여준다.

색상만으로 상태를 구분하지 말고 라벨 텍스트를 함께 표기한다.

# 19. 참가자 전투 화면

참가자 화면은 **자신의 페어를 관리하는 현장 전투 단말기**처럼 구성한다.
참가자는 자신의 페어 정보와 공개된 적 정보만 볼 수 있다.

## 19.1 상단 헤더

```text
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

TOWER RAID CONTROL SYSTEM

OPERATION : FIRST TOWER
FLOOR 37
ROUND 04

THREAT LEVEL : A

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

## 19.2 타깃 표시

그 아래 중앙에는 보스를 크게 표시한다.

```text
TARGET

[ 별을 먹는 짐승 ]

HP
██████████████░░░░░░
683 / 1000

PHASE 2

STATUS
DEF ↓
BURN
ENRAGED
```

## 19.3 헌터 패널

```text
HUNTER

NAME
서윤

STATUS
NORMAL

HP
78 / 100

ACTION POINT
● ● ● ○ ○
3 / 5

SKILL

[ 기본 공격 ]       AP 1
[ STAR SLASH ]      AP 2
[ BREAK EDGE ]      AP 3
[ 방어 ]            AP 1
[ 구조 ]            AP 2
[ ITEM ]
```

부상 상태는 명확하게 표시한다.

```text
NORMAL
INJURED
SEVERE
CRITICAL
DOWN
```

행동력이 부족한 행동은 비활성 상태로 표시하고, 왜 선택할 수 없는지 알 수 있게 한다.
쿨타임 중인 스킬은 남은 라운드를 함께 표시한다.

## 19.4 성좌 패널

헌터 패널과 대응되는 형태로 제작한다.

```text
CONSTELLATION

NAME
겨울을 삼킨 별

CONTRACT STATUS
RESONANCE

ACTION POINT
● ● ○ ○ ○
2 / 5

AUTHORITY

[ BUFF ]          AP 1
[ DEBUFF ]        AP 1
[ REVELATION ]    AP 2
[ MANIFEST ]      AP 3
[ FULL MANIFEST ] AP 5
[ RELIC ]
```

성좌 상태는 별도로 표현한다.

```text
STABLE
UNSTABLE
CRACKED
COLLAPSE
LOST
```

현신은 남은 사용 횟수를 함께 표시한다.

## 19.5 계약 상태 UI

헌터와 성좌 패널 사이에 **계약 연결 상태**를 표시한다.

```text
HUNTER
     ╲
      ╲
   CONTRACT
   RESONANCE
      ╱
     ╱
CONSTELLATION
```

또는:

```text
CONTRACT LINK

████████████████░░░░

STATUS : RESONANCE
```

계약 단계가 올라가면 UI 효과도 조금씩 변화하게 한다.

* 안정: 기본
* 공명: 별빛 효과
* 고조: 라인 또는 문양 활성화
* 불안: 깜빡임
* 균열: 글리치
* 붕괴: 붉은 경고

애니메이션은 과하지 않게 한다. `prefers-reduced-motion`을 존중한다.

## 19.6 페어 연계 표시

헌터와 성좌의 행동을 선택하면 가운데에서 연계 가능 여부를 보여준다.

```text
PAIR LINK ANALYSIS

CONSTELLATION
DEFENSE DOWN

+

HUNTER
STAR SLASH

━━━━━━━━━━━━━━━━━━

COMBINATION AVAILABLE

《 STAR BREAK 》

Expected Effect
+30% Damage
Ignore Defense 20%
```

연계가 불가능하면 다음만 표시한다.

```text
NO COMBINATION
```

## 19.7 행동 확정

화면 하단에 큰 버튼을 둔다.

```text
[ CONFIRM ACTION ]
```

확정 후:

```text
ACTION SUBMITTED

Waiting for Raid Control...
```

운영진이 결과를 처리할 때까지 수정 불가로 할지, 취소 버튼을 제공할지는 **설정 가능하게** 한다.

자동 위임된 쪽은 참가자가 행동을 고르지 않아도 확정할 수 있어야 한다.
한쪽이 이탈한 페어에서 남은 참가자가 확정 버튼을 누르지 못하고 막히는 상황이 생기면 안 된다.

## 19.8 레이드 로스터

레이드에서는 참가자 화면에도 다른 페어의 상태를 표시한다.

```text
RAID ROSTER

PAIR 01   READY     HP 78%   AP 3/2
PAIR 02   WAITING   HP 82%   AP 5/5
PAIR 03   AUTO H    HP 61%   AP 5/4
PAIR 04   DOWN      HP  0%   AP 5/5
```

* 자기 페어와 함께 공략 중인 페어의 제출 상태를 확인할 수 있다
* `AUTO` 위임 여부를 표시한다
* 적의 다음 패턴은 계시로만 공개된다

## 19.9 같이 싸우는 사람

연계는 **상대가 무엇을 할 수 있는지 알아야** 맞출 수 있다.
그래서 참가자 화면에도 함께 싸우는 사람의 스탯과 스킬을 보여준다.

```text
내 페어      헌터 · 성좌 두 장 — 내 캐릭터에 표시가 붙는다
다른 공략조  접어 두고, 펼치면 스탯 · 스킬을 본다
```

전투에 들어간 값(전투 상태)을 보여준다 — 시트 원본이 아니라 지금 싸우는 수치다.

## 19.10 화면은 스스로 갱신된다

참가자가 새로고침을 눌러야 진행이 보이는 화면은 쓸 수 없다.

```text
배정 대기    편성 → 전투 시작 두 단계를 보여주고, 전투가 열리면 자동 입장
전투 중      라운드 처리 결과 · 상대의 제출이 자동으로 반영된다
지금 할 일   화면 맨 위에 한 줄로 안내한다 (행동을 고르세요 / 제출 완료 · 대기 …)
```

서버 모드에서 참가자는 전투 상태를 쓰지 않는다. **자기 쪽 제출만** 보내고
나머지는 구독으로 받는다. 제출이 서버에 닿지 않으면 화면에 그대로 알린다.

`AUTO` 위임은 전투 상태 변경이므로 관리국이 설정한다.

## 19.11 채팅

참가자와 운영진이 같은 창을 본다. 채널은 전투 단위이고, 전투 밖에서는 전체 채널을 쓴다.

```text
대사 · 행동   진행. 대사와 행동을 한 글에 함께 적는다
잡담          진행 외 이야기
```

**두 보기는 섞이지 않는다.** 진행을 놓치지 않기 위해서다.
판정(다이스)은 어느 쪽에서 굴려도 **양쪽에 보인다** — 결과는 모두가 알아야 한다.

```text
/roll 2d6+3   또는  /r d20      어느 보기에서나 쓸 수 있다
```

기믹 선언과 그 판정은 확정하는 순간 채널에 자동으로 올라간다.

# 20. 운영진 화면

운영진 화면은 **관리국 중앙 작전실**처럼 만든다.
한 화면에서 모든 페어의 행동을 확인할 수 있어야 한다.

## 20.1 상단

```text
HUNTER MANAGEMENT AGENCY
CENTRAL RAID CONTROL

OPERATION : FIRST TOWER
FLOOR : 37
ROUND : 04

ACTIVE PAIRS : 12
INJURED : 3
DOWN : 1
```

## 20.2 페어 모니터

모든 페어를 작은 카드 형태로 표시한다.

```text
PAIR 01

HUNTER
서윤
HP 78%
AP 3

CONSTELLATION
겨울을 삼킨 별
AP 2

ACTION
STAR SLASH
+
DEF DOWN

LINK
STAR BREAK

STATUS
READY
```

상태:

```text
WAITING
READY
PROCESSING
DONE
ERROR
```

필터를 제공한다.

```text
ALL
GOVERNMENT
GUILD
INJURED
DOWN
NOT SUBMITTED
```

## 20.3 전체 전투 상황판

운영진 화면 중앙 또는 상단에는 보스 정보를 크게 보여준다.

```text
TARGET STATUS

STAR DEVOURER

HP
683 / 1000

PHASE
2 / 3

BUFF
ENRAGED

DEBUFF
DEF DOWN
BURN x2

NEXT PATTERN
UNKNOWN
```

운영진만 다음 패턴을 볼 수 있게 할 수도 있다.

```text
ADMIN ONLY

NEXT PATTERN
CONSTELLATION EATER

TRIGGER
ROUND 5
```

## 20.4 전투 처리

운영진은 모든 행동을 확인한 뒤 다음을 누른다.

```text
[ PROCESS ROUND ]
```

처리 전에는 예상 결과를 표시한다.

```text
PAIR 01    Damage 37
PAIR 02    Damage 21
PAIR 03    Defense

TOTAL DAMAGE
58
```

그리고 다음을 눌러 실제 HP와 상태를 변경한다.

```text
[ APPLY ]
```

**APPLY 전 단계에서 자동 계산 결과를 운영진이 직접 수정할 수 있어야 한다.**
피해량, 연계 성립 여부, 상태이상 부여 여부를 모두 덮어쓸 수 있어야 한다.

## 20.5 참가자 시트 열람

운영진은 **모든 참가자의 시트 전문을 볼 수 있어야 한다.**
스탯과 커스텀 스킬의 특수 효과를 모르면 기믹 판정도 연출도 쓸 수 없다.
참가자끼리는 서로의 시트 **전문**을 볼 수 없다 (`sheets` RLS — 본인 또는 운영진).
대신 공개분만 담은 프로필이 따로 있다 — 20.7 을 본다.

세 곳에서 본다.

```text
참가자 시트 탭    등록된 시트 전체 — 헌터/성좌/미편성 필터 + 검색
편성 탭           페어 카드 안에서 두 사람의 시트를 나란히
전투 · 페어 모니터  판정 중 스탯 · 스킬(쿨타임 · 남은 횟수) 확인
```

한 장에 담는 정보:

```text
활동명 · 역할 · 클래스(권역) · 소속
스탯 (배분값)
전투 환산 수치 (HP · ATK · DEF · AP · 권능 배율)
커스텀 스킬 — AP · 수치 · 쿨타임 · 사용 횟수 · 부여 상태이상 · 특수 효과
계약 상대 (참가자가 적어 둔 이름 — 공란 가능)
컨셉 — 성격 · 특징 · 계약 경위
편성 여부 (PAIR 라벨 또는 미편성)
```

참가자 시트 탭은 **시트 전문**과 **프로필 카드** 두 가지 서식으로 볼 수 있다.
전체 인원을 카드로 늘어놓는 화면은 이 탭에만 있다 — 참가자 화면에는 없다.

전투가 시작된 뒤에는 **시트 원본이 아니라 전투 상태의 값**을 보여준다.
운영진이 전투 중 수치를 고칠 수 있으므로, 판정 근거는 전투 상태 쪽이 맞다.

## 20.6 참가자 시트 편집 · 삭제

운영진은 시트를 **읽는 것에서 멈추지 않는다.** 이름 · 계약 상대 · 클래스 · 소속 ·
스탯 · 스킬(수치와 특수 효과) · 컨셉 세 칸을 직접 고칠 수 있어야 한다.

```text
배분 규칙(POINT_BUY)은 안내만 하고 막지 않는다
  → 보정이 필요한 경우가 있고, 판단은 운영진이 한다 (원칙 3)
이미 시작된 전투의 수치는 바뀌지 않는다
  → 전투 상태가 원본이므로 페어 모니터에서 따로 조정한다
```

시트 삭제도 운영진이 한다. 계정(auth) 자체는 남고 시트만 지워지며,
편성 기록(`pair_bonds`)에는 이름이 그대로 남는다.

## 20.7 프로필 — 제출한 시트는 전부 공개한다

참가자끼리 서로의 캐릭터를 읽는 것이 이 커뮤니티의 목적이다.
그래서 **시트에 적어 낸 것은 가리지 않는다.** 경계는 `config/characters.ts` 의
`SHEET_DISCLOSURE` 한 곳에 적혀 있고, 화면 안내 문구가 그 목록을 그대로 읽는다.

```text
공개 (다른 참가자)
  사진 · 이름(성호) · 헌터/성좌 · 클래스(권역) · 소속 · 계약 상대
  성격 · 특징 · 계약 경위
  스킬 — 이름 · 종류 · 설명 · AP · 위력 · 쿨 · 사용 횟수 · 부여 상태
  스탯 배분값 · 환산 전투 수치 (HP · ATK · DEF · AP · 권능)
  페어 공용 포인트와 보급품

비공개 (관리국) — 시트가 아니라 운영 정보다
  계정(로그인 · 비밀번호)
  포인트 지급 · 차감과 보급품 구매 · 반납 권한
  전투 기록 전문과 정산 내역
  전투 중 조정한 수치 (시트가 아니라 전투 상태 쪽 값)
```

`sheets` 의 RLS 는 그대로 "본인 또는 운영진"이다. 남의 시트 행을 직접 읽지는 못하고,
`public_profiles` 뷰를 통해서만 본다 — 뷰가 계정 소유 정보를 걸러 내는 자리다.

**한 명당 한 장**이며 서술은 잘리지 않는다. 비워 둔 칸도 자리를 남긴다 —
무엇을 안 적었는지도 정보이기 때문이다.

두 쪽의 인상을 갈라 놓는다.

```text
헌터   관리국 단말이 쏘아 올린 홀로그램
       주사선 · 청록 번짐 · 비스듬한 빛 쓸림 · 모서리 브래킷 · 송출 표시등
성좌   성물함에 든 성록(星錄)
       위에서 내려오는 후광 · 방사형 광선 · 금박 이중 테두리 · 광배 · ✦ 구획선
```

스탯은 게임 상태창처럼 세 겹으로 보여 준다.

```text
레이더   스탯 수만큼의 다각형. 라이브러리 없이 SVG 로 그린다
         헌터는 단말이 훑은 스캔 도형, 성좌는 별자리 그 자체가 된다
게이지   정확한 값은 여기서 읽는다 — 상한 대비 채움
환산 타일 HP · ATK · DEF · AP (성좌는 권능 배율 · AP) 를 큰 숫자로
```

성좌 카드는 전부 가운데 정렬이므로 스탯 창도 도형을 위, 수치를 아래로 세운다.
가방은 인벤토리 격자로 놓고, 분류마다 위 테두리 색을 달리해 훑기 쉽게 한다.

주소 하나로 한 명을 열 수 있다. 운영진이 이 주소를 커뮤니티에 남긴다.

```text
/battle/sheet/?id=활동명
  참가자 시트 탭 → 프로필 카드 서식 → 카드 밑에 주소와 복사 버튼
  로그인하지 않아도 읽힌다 — 커뮤니티에 그대로 붙이는 주소다
```

링크를 아는 사람은 누구나 그 시트를 본다. 대신 편성 · 전투 기록 · 계정은 닫혀 있다 —
비로그인 화면에서는 관리국이 맺어 준 페어 정보가 빠지고, 시트에 적어 둔 페어명과
계약 상대 이름만 뜬다.

전체 인원을 카드로 늘어놓는 화면은 작전실에만 있다.
참가자 화면은 자기 프로필과 편성된 페어 상대 한 장만 본다.

## 20.8 페어명 — 참가자가 적고, 관리국이 묶는다

시트에 **페어명** 칸이 있다. 짝을 정하고 온 두 사람이 같은 이름을 적어 낸다.

```text
참가자   시트에 페어명을 적는다 (공란 가능 — 아직 안 정했으면 비운다)
관리국   편성 탭의 "페어명 묶음" 에서 같은 이름끼리 묶인 목록을 본다
         띄어쓰기와 대소문자는 무시하고 맞춘다
         헌터 1 · 성좌 1 로 맞아떨어지면 한 번에 계약을 성립시킨다
         맺어진 페어의 라벨이 곧 그 페어명이다 (나중에 고칠 수 있다)
```

한 조에 세 명 이상이 같은 이름을 적었거나 한 쪽만 있으면 묶음에 사유가 뜬다 —
그때는 위쪽 선택칸에서 직접 고른다.

페어 상대 이름은 두 갈래로 정해진다.

```text
편성 전   참가자가 시트에 적어 둔 이름 (공란 가능)
편성 후   관리국이 맺어 준 pair_bonds 의 이름이 우선한다
```

## 20.9 보스 패턴 — 직접 만든다

프리셋 패턴 세트(`config/patterns.ts`)만으로는 층마다 다른 연출을 만들 수 없다.
운영진은 **패턴 전체를 직접 설정한다** — 페이즈가 넘어가는 지점, 공격,
그 공격이 나오는 라운드까지.

### 공격 하나가 가지는 것

```text
이름 · 연출 문구
피해 계수        적 공격력 × 계수 (0 이면 피해 없이 연출 · 상태이상만)
범위             단일 / 광역
예고 라운드      0 이면 즉시, 1 이상이면 그만큼 예고한 뒤 발동
예고 문구
이름 공개 여부   비공개면 참가자에게 UNKNOWN 으로 보인다
부여 상태이상    맞은 쪽 / 자신
사용 페이즈      비우면 모든 페이즈
라운드 주기      2 이상이면 그 주기의 정해진 자리에서만 (예: 3라운드마다 1번 자리 → 1 · 4 · 7)
주기 안의 자리   같은 주기에 여러 공격을 흩어 놓는다
HP 조건          적 HP 가 이 비율 이하일 때만 (0 이면 조건 없음)
```

### 페이즈 경계

```text
페이즈 수        1~5
전환 HP%         PHASE n → n+1 로 넘어가는 HP 비율. 내림차순으로 정한다
                 [70, 30] 이면 HP 70% 이상 PHASE 1, 30% 이상 PHASE 2, 그 아래 PHASE 3
비워 두면        프리셋 세트의 경계를 쓰고, 그것도 없으면 페이즈 수만큼 균등 분할한다
```

경계를 손대지 않은 층은 지금까지와 똑같이 동작한다.

### 동작 규칙

```text
커스텀 공격이 하나라도 있으면 프리셋 패턴 세트는 쓰지 않는다
조건(주기 · HP)이 걸린 공격이 먼저 나가고, 조건이 겹치면 목록에서 위에 있는 쪽이 이긴다
조건 없는 공격은 남은 라운드를 순서대로 돌아간다 (운영진이 순서를 예측할 수 있어야 한다)
어느 공격도 걸리지 않은 라운드에는 아무것도 하지 않는다
```

### 프리셋 불러오기 · 진행표

프리셋은 코드에 있어 고칠 수 없다. **프리셋 불러오기**를 누르면 그 세트가
편집 가능한 공격 목록과 페이즈 경계로 펼쳐진다 — 예고와 본체는 한 공격으로 합쳐지고,
트리거의 주기 · 페이즈 조건도 그대로 따라온다. 이후에는 그 보스만의 패턴이 된다.

편집 화면에는 **진행표**가 함께 나온다. 페이즈별로 1~6 라운드에 어떤 공격이 나오는지를
저장 전에 확인할 수 있다 (HP 조건은 그 페이즈 구간의 가운데 HP 를 기준으로 계산한다).

전투 중에도 페어 모니터 옆 적 카드에서 공격 목록과 페이즈 경계를 고칠 수 있다 —
다음 라운드 선택부터 반영된다.

# 22. 전투 로그

모든 행동은 전투 로그에 기록한다.

## 22.2 연출 로그

운영진이 커뮤니티 진행에 바로 붙여 쓸 수 있는 형태의 텍스트를 제공한다.

```text
─ ROUND 3 ─

「겨울을 삼킨 별」의 빛이 전장을 뒤덮습니다.

HP
720 → 683
```

연출 로그는 자동 생성 후 운영진이 수정할 수 있어야 한다.

연출 문구 템플릿도 설정 데이터로 분리해 수정할 수 있게 한다.

# 23. 정부 vs 민간 길드 표현

사이트 자체는 헌터 관리국 시스템이지만, **민간 길드 참가자를 정부 소속처럼 표현하면 안 된다.**

관리국이 공동 공략에 참여하는 모든 페어를 모니터링하고 있다는 설정으로 처리한다.

따라서 페어 카드에는 소속만 표시한다.

```text
AFFILIATION

GOVERNMENT
```

```text
AFFILIATION

PRIVATE GUILD
```

민간 길드 캐릭터도 같은 시스템에서 조회되지만 관리국 소속이라는 의미는 아니다.
UI가 한쪽 진영에 유리하거나 불리하게 보이지 않도록 한다.

# 24. 성좌 요소

관리국 UI라고 해서 성좌가 단순 수치로만 보이지 않도록 한다.

성좌 관련 부분에는 다음을 **제한적으로** 사용한다.

* 별자리 라인
* 성흔 문양
* 별빛 입자
* 계약 연결선
* 현신 시 화면 왜곡
* 권능 사용 시 문양 활성화

전체적으로 다음 인상을 목표로 한다.

> **현대의 인간이 이해할 수 없는 초월적 존재를 억지로 전산 시스템에 측정해서 표시하고 있는 느낌**

예:

```text
CONSTELLATION OUTPUT

MEASUREMENT ERROR

■■■■■■■■■■■■■■■■

LIMIT EXCEEDED
```

이런 연출도 사용할 수 있다. 단 가독성을 해치는 지점에서는 쓰지 않는다.

# 28. 구현 우선순위

한 번에 모든 기능을 완성하려고 하지 말고 다음 순서로 구현한다.
**각 Phase가 끝나면 빌드와 동작을 검증하고 멈춘다.**

### Phase 1 — 전투 기본

* 헌터 / 성좌 / 적
* HP / 행동력 / 라운드
* 기본 행동, 행동 선택, 행동 확정
* 다수 페어(레이드) 데이터 구조
* 자동 행동

### Phase 2 — 스킬

* 커스텀 스킬
* 버프 / 디버프 / 상태이상
* 쿨타임

### Phase 3 — 페어

* 페어 연계
* 현신 / 구조 / 기믹

### Phase 4 — 보스

* 보스 패턴 / 페이즈 / 예고 / 특수 기믹

### Phase 5 — 운영

* 운영진 화면
* 결과 수정
* 전투 로그
* JSON Export / Import

### Phase 6 — 확장 (완료)

* 포인트 / 아이템 / 상점 연동
  * `config/items.ts` · `config/rewards.ts` · `config/shop.ts`
  * 아이템 행동(`hunter.item` / `const.relic`)은 고른 아이템이 비용과 대상을 정한다
  * 포인트 지급은 원장(`BattleState.rewards`)에 이유와 함께 남는다
  * 구매는 전투 밖 보급 창구에서만 — 전투 중에는 보유량만 본다
* 공략 기록 / 전투 기록 보관
  * `engine/record.ts` — 끝난 전투를 스냅샷으로 보관하고, 정산으로 편성에 반영한다

# 29. 중요한 구현 원칙

**1. 수치를 코드 곳곳에 하드코딩하지 않는다.**
행동력, 스킬 비용, 보상, 부상 기준 등은 설정 데이터에서 수정 가능하게 한다.

**2. 참가자 UI와 운영진 UI를 분리한다.**
참가자는 필요한 정보만 보고, 운영진은 전체 데이터를 관리한다.

**3. 자동 판정이 운영진보다 우선해서는 안 된다.**
자동 계산 결과를 운영진이 언제든 수정할 수 있어야 한다.

**4. 커스텀 스킬을 전제로 설계한다.**
정해진 스킬 목록만 사용하는 시스템으로 만들지 않는다.

**5. 페어 연계 조건 역시 데이터화한다.**
추후 새로운 연계를 코드 수정 없이 추가하기 쉽게 만든다.

**6. 전투 규칙과 UI를 최대한 분리한다.**
추후 규칙이 변경되어도 UI 전체를 다시 만들 필요가 없어야 한다.

**7. LocalStorage는 임시 저장 계층으로 취급한다.**
추후 서버 또는 Supabase를 연결할 수 있도록 저장 인터페이스를 분리한다.

**8. GitHub Pages에서 정상적으로 동작해야 한다.**
저장소의 `base` 경로(`/StartHunter`)에서도 CSS, JS, 이미지 등의 경로가 깨지지 않아야 한다.
내부 링크는 `import.meta.env.BASE_URL`을 기준으로 생성한다.

**9. 기존 소개 페이지를 건드리지 않는다.**
`src/pages/index.astro`와 `src/styles/global.css`의 기존 동작은 유지한다.
